# Observer-side performance and latency survey (2026-11-09)

## Decision boundary and source

Survey only, at `origin/develop` `9fdac8d45c98df4ea034ad69c538765b8ce77e8a` in a dedicated worktree. No runtime or configuration change is proposed for immediate shipment. The owner has declined the Codex append-only assumption and weaker read guarantees; this survey does not reopen them. Socket exchange and checkpoint persistence internals belong to the separate transport survey.

The current default is a 10,000 ms refresh interval, 2,000 ms reader budget and 60,000 ms usage maximum age (`src/config.rs:22-32`). The interval is configurable from 1,000 to 3,600,000 ms, subject to the reader timeout and age constraints (`src/config.rs:66-80`). The 5 s default in some historical records describes older source, not this revision. `TODO.md` keeps period/event-driven refresh conditional on an event-to-visible definition and Linux/macOS measurements.

## From a source change to the sidebar

| Boundary | Current path | Delay or uncertainty |
| --- | --- | --- |
| Agent state | Herdr's authoritative pane snapshot carries `agent_status`; the plugin parses it and derives `lineup_state` (`src/protocol.rs:172-176`, `src/tokens.rs:160-168`). | A working/idle/blocked/done transition may miss the snapshot and wait for another refresh. A statusLine file watcher cannot detect this transition. |
| Source observation | Claude/Agy invoke `statusline`, which reads up to 1 MiB of hook input, parses it and atomically replaces a small record (`src/statusline.rs:157-214,328-344`). Codex/Kimi/Grok observe local files through their provider readers (`src/reader_codex.rs:82-155`, `src/reader_kimi.rs:73-100`, `src/reader_grok.rs:86-117`). Git reads the locally known `origin/main` ref, never fetches (`src/ship_time.rs:25-27,373-453`). | The provider's own write or hook cadence is outside Lineup's control. Git remote changes are invisible until another process updates the local ref. |
| Wait for refresh | The daemon starts immediately, then schedules the next start at completion plus `refresh_interval_ms`; it sleeps in 100 ms increments (`src/daemon.rs:1016-1018,1075-1077,1113-1119,33`). | With an otherwise successful, short cycle and no missed snapshot, phase wait is roughly 0–10 s plus up to one idle sleep and scheduler delay. This is a code-derived approximation, not an upper bound. A change after the snapshot can wait through the current cycle and the following post-cycle interval. |
| Inventory and heading | A refresh takes one authoritative session snapshot, then resolves Git headings (`src/publish.rs:1764-1769,2354-2369`). Heading reads have a shared one-second cycle term and at most four concurrent observations (`src/publish.rs:81-91,1839-1953`); each query has a one-second cooperative cap (`src/ship_time.rs:50-54,197-221`). | Unique repositories consume Git children and stat I/O; fair admission can defer a heading. A failed or unattempted heading may use a confirmed fallback for under 30 s; unknown clears it (`src/publish.rs:1059-1113`). The cap is not a strict wall-clock guarantee during blocked kernel I/O or reaping. |
| Pane observation | The cycle has one reader deadline starting after headings; each pane gets the remaining budget and a fresh read clock (`src/publish.rs:2354-2375,2095-2160`). `ReadCycle` shares validated discovery names only within that refresh (`src/model.rs:125-134,254-331`). | Earlier pane work, discovery and budget exhaustion can defer or omit a fresh value. Reader timeout is shared across panes, not multiplied by pane count. |
| Publication and display | The send pass plans each pane/workspace and reports desired metadata (`src/publish.rs:2378-2425`). The existing isolated latency record measures a synthetic request to a **stored token**, not a rendered sidebar frame. | Metadata transport, Herdr storage and UI rendering add delay not measured here. A changed token does not have to wait for the three-interval live-key TTL; TTL protects against stale publication and is not an initial delay (see `latency-investigation-2026-11-04.md`). |

The source-to-render path therefore has no proven bound or SLO. The nine prior Linux synthetic state-request trials bracketed stored-token observation at 0.929–1.115 s (late phase), 4.844–5.198 s (mid) and 9.666–9.973 s (early); their event was a synthetic `report-agent` request, not a provider-file write or visible frame (`latency-investigation-2026-11-04.md`, section B). The phase spread is consistent with post-cycle polling but does not estimate a production distribution.

## Observer work and measurement

This run used the existing ignored `publish::tests::measure_refresh_stages` fixture (`src/publish.rs:6362-6465`): one synthetic Git repository, 1/8/32/128/256 panes, three fresh cold publishers at each size, fixed `SampleReader`, default config, fake Unix socket with `LINEUP_BENCH_ROOT=/tmp` and `LINEUP_BENCH_REPEATS=3`. The test creates managed temporary directories there and cleans them up. A later `df -T` identified `/tmp` as **tmpfs** and the worktree filesystem as **ext4**; the filesystem was not captured during the three-second measurement, so the same mount during that interval is inferred. The only test child used an environment with all inherited `HERDR_*` keys removed. No real Herdr process, session, provider home, network API or user configuration was touched. Build products stayed in this worktree's `target`. Pinned Rust and locked dependencies; `cargo test --locked --lib --no-run -j 2` built the library test binary (`SHA-256 84fc1d92070e60253af8953329bf7fd3d872a40b8bb01e6c6503fd8777d30fe1`). The test exited 0, running exactly one ignored test, in 3.454 s, from 2026-11-09 11:39:58.292681 to 11:40:01.746523 UTC. The 1/5/15-minute load averages were 6.19/5.77/8.41 before and after on a host reporting 24 processors. Other lanes were active and their work was not controlled; the load average is not CPU utilization. Measurement was well under the 30-minute limit.

These stage intervals overlap: socket includes snapshot exchange and persist is inside the report path (`src/publish.rs:913-934`). Do not add columns or subtract them from refresh. **This tmpfs fixture's persist and refresh values are not representative of a real-disk checkpoint.** The earlier ext4 observations recorded persist medians of about 8.9–75.7 ms across different fixtures/source snapshots (`latency-investigation-2026-11-04.md`, section A; `stage-timing-comparison-2026-11-04.md`, Independent medians). They are not a paired comparison with this run. The reader is a fixed-value test double and its microseconds cannot represent provider discovery. The fixture's one shared repository also cannot represent many unique Git roots. The previous wired Git matrix measured three children per completed repository observation and normal distinct/32 p50 about 1,001 ms, near the one-second cycle budget (`git-heading-latency-wired-2026-11-04.md`, Results). The separate real-disk discovery matrix found, for example, Codex 3,000 candidates/32 panes median 16.342 ms and p95 38.388 ms, with warm caches and uncontrolled load (`reader-discovery-real-disk-2026-11-04.md`, Main table). Those separate profiles cannot be summed with this run or used to infer real end-to-end latency. The Codex parser trial's pooled full-call median improved only 4.491%, below its 10% gate, with highly variable blocks (`codex-reader-perf-trial-2026-11-04.md`). The ten-minute live doctor sample saw 3 deadlines/1,880 Codex attempts and no BUSY rejections, but cannot establish long-term stall frequency (`stuck-worker-frequency-2026-11-04.md`).

Not measured: actual source-write timestamp to reader observation; macOS; release binary; populated provider homes in this run; real-disk checkpoint/persist and refresh time; Git ref-change freshness under a real workload; CPU time or syscall counts; a configured shorter interval; Herdr storage or rendered-frame time; failure, reconnect, admission, stale-key or degraded-TTL tails. The existing doctor stage histogram is aggregate and cannot correlate one source event with one frame. The refresh's cooperative envelope sums a 2 s snapshot term, 1 s Git term, 2 s reader term and 2 s metadata term at defaults (`src/publish.rs:81-91,2362-2366`); synchronous I/O or reaping can exceed it. These gaps prevent a claim that 10 s is optimal or that any option below will improve perceived latency.

## Ranked follow-ups (estimated opportunity, not implementation approval)

The order below is by plausible reduction for an eligible **local context/quota** change arriving just after a snapshot. For **Herdr agent state** (`lineup_state`), item 1 is inapplicable: item 2 is the first applicable experiment, and a separate Herdr event signal would be needed for event-triggered state refresh. For **Git headings**, item 3 can move up when there are many unique roots. Thus these are signal-specific priorities, not a single measured cross-signal ranking. Effects overlap and must not be added. Each option needs an agreed freshness/load acceptance contract before implementation.

1. **Coalesced local wakeup for context/quota source changes, retaining periodic reconciliation.** (a) Evidence: the statusLine hook writes its context/quota record without notifying the daemon (`src/statusline.rs:157-214,328-344`); the daemon waits only for its timer (`src/daemon.rs:1075-1119`). The 10 s opportunity is code-derived; the prior 9.666–9.973 s synthetic bracket measured **agent state** and is not evidence of a hook-to-frame gain. (b) Potentially removes most of the remaining 10 s phase wait for eligible local context/quota changes; it cannot detect `agent_status` changes in Herdr. Actual benefit depends on hook cadence, event delivery, refresh cost and UI time. (c) Watcher loss/overflow, atomic rename, path replacement, symlink rules, burst storms and Linux/macOS differences could miss events, increase CPU/I/O or weaken freshness; periodic full reconciliation and current validation must remain. (d) Large, cross-platform runtime and test work. (e) Define source-event and rendered-frame timestamps; compare event-enabled and periodic-only isolated Herdr sessions on Linux/macOS, including burst, lost-event, rename, failure and idle-resource tests, with CPU, Git children, reader scans and tail latencies. Track context/quota separately from agent state.
2. **Bounded interval trial before changing the 10 s default, applicable to agent state and local sources.** (a) Evidence: `src/config.rs:22-32,66-80` permits 5 s with the current 2 s reader timeout; 1 s requires reducing that timeout to at most 1 s. `src/daemon.rs:1113` starts the wait after completion. The previous synthetic **agent-state** phase brackets show polling wait dominates small isolated cycles. No shorter-interval comparison was run here. (b) Halving the interval could reduce nominal phase wait by up to about 5 s for a short successful cycle; it can increase refreshes and local Git children approximately twofold. That is an arithmetic estimate, not a measured benefit or cost. (c) Higher CPU/I/O, battery use, log churn and admission pressure; still no bound under long cycles, skipped resources or UI delay. (d) Small configuration experiment, but medium decision/validation work; no user config change is requested here. (e) With isolated settings and no real session, alternate 10 s/5 s runs under matched pane/repository/provider fixtures on both OSes; record separate agent-state and context/quota source-to-render quantiles, process CPU, filesystem I/O, Git child counts, skipped reports and expiration, then choose against explicit thresholds.
3. **Reduce repeated Git work only after proving equivalent invalidation.** (a) Evidence: each completed observed repository uses three Git children even on cache hit (`src/ship_time.rs:156-162,373-527`); the wired matrix's distinct roots approach the one-second cycle term. The current cache safely avoids `worktree list` but still obtains ref time and verifies ownership/config/dependency fingerprints. (b) Possible CPU/I/O saving and fewer deferred headings for many unique roots; no measured improvement or safe child-count reduction exists. It is unlikely to matter for one shared root, and does not remove the 10 s timer wait. (c) Skipping native checks can accept an unsafe directory or stale/replaced ref; loose/packed refs, replacement refs, includes, linked worktrees and race windows require identical semantics. (d) Medium to large. (e) Prototype only in an isolated worktree, retain all refusal and race fixtures, measure real Git child/syscall counts and heading freshness across same/distinct/linked repositories, then compare against a predeclared gain threshold on both OSes.
4. **Target repeated provider discovery only when the full reader is a measured bottleneck.** (a) Evidence: `ReadCycle` already reuses validated names across panes but revalidates ancestor/directory stamps and begins anew each refresh (`src/model.rs:125-134,208-218,254-331`); the separate real-disk matrix records low tens of milliseconds at 32 panes for its warm fixtures. (b) Potential CPU/I/O saving in unusually large provider homes; likely small contribution to ordinary event latency relative to the 10 s phase wait. (c) Cross-cycle name reuse can miss duplicates, replacement, permissions or same-size rewrites and change `MissingReason`. (d) Medium. (e) First profile populated, synthetic homes with source-event timestamps and CPU/syscall counts; require exact outcome equivalence under duplicate, rename, symlink, permission and truncation fixtures before testing a prototype.

## Avoid

- **Do not implement a pure append-only Codex reader or relax validation.** The owner explicitly rejected that assumption, and the earlier parse trial missed its benefit gate. It risks stale/corrupt observations and changed missing reasons.
- **Do not turn the refresh interval down globally without an event-to-visible and resource-cost contract.** More polls can be expensive while Herdr rendering remains unmeasured.
- **Do not remove per-cycle Git ref/ownership checks solely because the heading cache is warm.** A hit currently retains native verification and three child invocations by design; removing them without equivalence proof risks stale or unsafe headings.
- **Do not use the cold fixture's tiny injected-reader duration to justify dropping reader timeouts or safety checks.** It does not execute real provider I/O, and the cooperative deadlines protect against stalls.
