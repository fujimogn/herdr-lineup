# Font action atomicity policy (2026-10-23)

## Decision in brief

The unreviewed `79196492940e4266a0182aca4dd27e188cacbf51` candidate improves the `b5fc3114565f63d6fc5765a36d69dcf3ba47f3a0` baseline: it compares file identity and bytes before rollback, checks the font again before removal, and adds injected conflict tests. These are useful best-effort protections, **not a guarantee against an uncooperative editor**. Each check remains separate from the following pathname-based `rename` or `unlink`. Neither the portable API used by this crate nor the OS-specific APIs cited below offer a conditional "replace or unlink this name only if it still denotes this inode and these bytes" operation. Do not describe H1/M1 as fully closed or ship this policy as implemented.

The smallest policy with a defensible preservation claim is to **stop automatic destructive recovery when ownership is uncertain**, retain the ownership record and any displaced file for inspection, and report a conflict with exact paths. That changes current rollback and uninstall behavior and requires owner approval. Until that decision, the candidate's checks can reduce common races, but an absolute external-edit preservation claim is unavailable. No implementation change is made here.

### Concrete interleavings

1. **H1 baseline, reproduced by candidate tests:** Lineup writes kitty; an editor appends to kitty; a later Ghostty write fails; baseline rollback replaces kitty with the saved original. The candidate's `external_edit_after_our_write_survives_rollback` injects that order for both install and uninstall, and detects the conflict before rollback.
2. **H1 remains, not tested:** Lineup writes kitty and stamps it; a later write fails; `rollback_owned` stamps kitty and finds a match; an editor atomically renames a new kitty file into place; Lineup's `write_atomic` renames the original bytes over it. The editor's file is unlinked from the target path. The candidate's test inserts the edit before the stamp, not in this interval.
3. **M1 baseline, reproduced by candidate test:** Lineup plans removal of its font; a competing process replaces the font with identical bytes but a different inode; candidate's immediate stamp check detects the identity change. `same_byte_font_replacement_before_removal_is_preserved` covers this order.
4. **M1 remains, not tested:** The stamp check succeeds; another process replaces the font entry; `fs::remove_file` removes that replacement. `unlink` takes a pathname, not the previously opened inode.
5. **Journal remains, not tested:** Lineup compares the old journal with `require_bytes`; another process replaces it; `write_atomic` renames the new journal over it. Likewise, after `rollback_owned` stamps a candidate-owned journal, another writer can replace it before restoration or deletion.
6. **Absent target remains, not tested:** A terminal path is absent at planning or a rollback target is absent at its stamp check; another writer creates it before Lineup's final rename. Plain `rename` replaces the newly created entry. `create_new` for the font has different semantics and does not protect terminal or journal rename destinations.

The candidate tests use temporary homes and injected callbacks. They show specific scheduling orders, not a stress proof, kernel-level invariant, macOS execution, or behavior under a noncooperating process at every instruction boundary. `git diff b5fc311..7919649` is the evidence for implementation; this document does not claim those tests ran as part of this record-only lane.

## Available filesystem primitives and limits

| Option | Platform and feasibility | What is preserved on failure | Compatibility and rollback | Integration test needed |
| --- | --- | --- | --- | --- |
| Conditional rename/unlink by expected inode and bytes | **Unavailable in the cited portable API.** Linux `renameat2(RENAME_NOREPLACE)` rejects an existing *destination*; `RENAME_EXCHANGE` swaps names atomically. macOS `renameatx_np(RENAME_EXCL)` and `RENAME_SWAP` provide analogous name operations. None compare the existing source/destination identity or content with a caller-supplied expected value. `unlinkat` has no such flag. | No strict guarantee from a preceding stamp, even with `*at` directory descriptors. | Would require a new, proven OS primitive or mandatory cooperation from every writer; fail closed where unsupported. Do not silently fall back to ordinary rename/unlink while advertising a guarantee. | Separate process pauses precisely after identity check, then replaces or edits target; verify no claimed guarantee is contradicted on Linux and macOS. |
| Quarantine plus no-replace | Move a target to a unique same-filesystem quarantine name using Linux `RENAME_NOREPLACE` or macOS `RENAME_EXCL` when supported; never use plain rename to an occupied quarantine path. A normal same-filesystem rename to a unique name can still be used if collision is checked, but that check is itself racy. | Bytes moved out of the public path can survive even if they prove foreign after the move. This is preservation of recoverable content, **not preservation of the public path**. Another writer may create a new public entry before restoration; do not overwrite it. | Needs a retention location, ownership metadata, space bound, conflict output, manual recovery instructions, same-volume requirement, and handling for unsupported filesystem flags. Crash between move and restore needs a journal that identifies quarantine. A writer editing an open inode after the move can still change quarantined content. | Inject substitution before move, after move, and before no-replace restore; test collision, crash/restart, same-volume failures, unsupported flags, and exact recovery paths on APFS and supported Linux filesystems. |
| Shrink automatic rollback/deletion | On any uncertain stamp, write, or journal state, stop mutation, retain journal and current files, and return a conflict. More conservative variant: disable automatic rollback of terminal config and font deletion altogether, making recovery explicit. | Avoids a later destructive rollback/delete by Lineup, but an earlier ordinary `write_atomic` can already have replaced an external edit. Partial Lineup state remains until a user inspects it. | Changes present install/uninstall semantics and exit/reporting. Existing success and crash-recovery tests must be updated. Manual recovery must specify whether the managed block, font, and journal can be removed; do not auto-delete a journal while it may be the only recovery record. | Failure at each font/config/journal stage, external write before/after each mutation, no automatic deletion on unknown ownership, clear retry and manual recovery on both OSes. |
| Cooperative locking | Have all Lineup actions and participating editors honor the same lock, held through compare, mutation, and recovery. | Can serialize only cooperating processes. | Existing `FontLock` already covers Lineup actions; terminal editors and font managers need opt-in, so this is not a general user-data guarantee. | Two cooperating actions serialize; an uncooperative editor still wins the adversarial race. |

Primary sources: [Linux `renameat2(2)`](https://man7.org/linux/man-pages/man2/renameat2.2.html) documents destination atomic replacement, `RENAME_NOREPLACE`, `RENAME_EXCHANGE`, filesystem support, and NFS caveats; [Linux `unlinkat(2)`](https://man7.org/linux/man-pages/man2/unlink.2.html) documents pathname deletion and flags; [Linux `openat(2)`](https://man7.org/linux/man-pages/man2/open.2.html) explains directory descriptors protecting path prefixes, not the final name from replacement. Apple's [XNU `sys/stdio.h`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/stdio.h) declares `RENAME_EXCL`, `RENAME_SWAP`, and `renameatx_np`; [Apple's volume capability](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumesupportsexclusiverenaming) says exclusive rename depends on the volume; [Apple's `rename(2)` manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/rename.2.html) describes replacement of an existing destination. The conclusion about absent compare-and-delete/replace semantics is an inference from these documented interfaces, not proof that no private or future OS API could provide it.

## Recommendation and decision boundary

1. **Now, with no behavior change:** Keep `7919649` identified as an unreviewed best-effort candidate. Review its full fixed range before any integration. Wording must say it detects the tested pre-operation conflicts and leaves a residual check-to-mutation race. Keep `b5fc311` as the baseline for this record.
2. **Recommended minimal next implementation, subject to owner choice:** Fail closed on uncertain ownership, stop automatic destructive rollback/deletion, preserve the journal, and report a manual recovery path. If an action must replace a terminal config, consider an atomic exchange into retained quarantine so the displaced bytes remain recoverable. This still does not guarantee that an external edit remains at its original path. Bound retention and test APFS/Linux behavior before enabling it.
3. **Owner decision required:** Choose between (a) best-effort automatic recovery with explicitly limited guarantees, (b) conservative partial-state/manual recovery, and (c) a stronger external-edit preservation requirement that blocks font actions until a proven platform-specific or cooperative protocol exists. Also decide whether retaining displaced user files in quarantine is acceptable, how long to retain them, and whether automatic font uninstall should be disabled when ownership is uncertain. These alter user-visible behavior and recovery responsibility.

No proposed policy is implemented or verified by this document. No real font, terminal configuration, Herdr session, or user plugin state was touched. The Rust checks for this record-only worktree are reported separately with the candidate commit.
